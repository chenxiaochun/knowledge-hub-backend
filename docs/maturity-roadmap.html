背景与范围

当前系统在能力面已经较完整：文档解析与审核流水线、混合检索、Graph RAG、流式 Agent 对话、短/长记忆、ASR/TTS、RBAC 与团队可见性等。 本页从「能不能当成熟企业系统长期跑」出发，记录仍需补齐的缺口，并说明每一条问题的原因（为何会成为问题、不修会怎样）。

范围覆盖后端 knowledge-hub-backend 与配套前端 knowledge-hub-frontend。证据路径以仓库内文件为准；随代码演进可能偏移，以当时实现为准。

优先级说明

级别含义
P0 上生产或对外暴露前必须处理；否则有数据损坏、未授权访问或密钥失控风险。
P1 质量与运维硬伤；不修则难回归、难排障、用户会话体验脆弱。
P2 体验与加固；不阻塞上线，但影响「成熟产品」观感与长期可维护性。

建议先做的三条

若只开一轮迭代，优先：
  1. 正式 migration + 生产关闭 synchronize
  2. 鉴权 / 限流 / TTS WS 鉴权
  3. CI + 最薄 e2e（登录 → 提问 → 停止）
这三块不做，RAG/图谱再强也仍偏「演示系统」。

P0 · 上生产前必须处理

P0 TypeORM 常开 synchronize，缺少 migration

现象

应用启动时 TypeORM synchronize: true，会按实体自动改库表；仓库内未见正式 migration 流程。

原因
  • 课练/本地开发为省事常用 synchronize，实体加字段即可「自动有列」。
  • 生产若仍开启：并发启动、字段改名/删列可能导致静默改表甚至丢数据；多环境 schema 不可审计、不可回滚。
  • README 虽写「开发环境同步」，代码若未按 NODE_ENV 分支关闭，部署时极易带着 true 上线。
证据 / 落点

src/app.module.ts src/database/data-source.ts src/database/migrations/ README.md

进展

已搭 CLI DataSource、共用实体列表、baseline migration；运行时默认 synchronize: false（仅当 TYPEORM_SYNCHRONIZE=true 时开启）。 已有库勿盲目 migration:run baseline，见 README。

P0 JWT 可能回落到开发默认密钥

现象

未正确配置环境变量时，JWT 签名可能使用类似 dev-secret-change-me 的默认值。

原因
  • 本地一键跑通需要「没配也能启动」的兜底。
  • 生产若漏配 JWT_SECRET，攻击者可用公开默认密钥伪造任意用户 token，等于鉴权失效。
证据 / 落点

src/auth/auth.module.ts src/auth/jwt.strategy.ts

P0 缺少 CORS / helmet / 全局限流

现象

main.ts 主要挂了 ValidationPipe 与非生产 Swagger；未见 helmet、显式 CORS 策略、接口级 throttling（登录爆破、AI 刷接口）。

原因
  • 前后端同机代理开发时，CORS/安全头感知弱。
  • LLM/检索调用成本高，无限流时易被刷爆账单或拖垮 ES/LLM。
  • 缺少安全响应头会放大 XSS、点击劫持等浏览器侧风险面。
证据 / 落点

src/main.ts package.json（未见 throttler/helmet 依赖）

P0 Logout 不真正吊销 token

现象

登出接口存在，但 refresh token 无黑名单/轮换失效机制时，已泄露的 refresh 仍可换新 access。

原因
  • JWT 本身无状态：服务端「忘记」客户端删本地 token ≠ 服务端作废。
  • 成熟系统要求：登出、改密、风控封禁后，旧 refresh 立即失效。
证据 / 落点

src/auth/auth.controller.ts src/auth/auth.service.ts

P0 TTS WebSocket 缺少鉴权

现象

TTS 中继 WebSocket 若仅依赖 sessionId 查询参数，知道或猜到会话 id 即可连上听/抢流。

原因
  • 课练阶段优先打通「问答文本 → 腾讯云 TTS」链路，鉴权后置。
  • sessionId 常出现在 URL/日志/前端状态中，熵不足时等同半公开信道。

P0 生产交付物缺失；compose 弱口令

现象

缺少面向部署的 Dockerfile / .env.example；本地 docker-compose.yml 使用弱口令且多中间件端口直接映射。

原因
  • 本地开发追求「clone 即起」：固定账号密码写死在 compose 很常见。
  • 若把同一套口令或端口暴露策略带进生产/公网预览，数据库与消息队列会被扫库。
  • 无 .env.example 时，新成员与部署清单只能翻代码猜键名，易漏配关键密钥。

现象

部分接口使用 @Public()，未登录即可访问（例如团队树）。

P1 测试与 CI 几乎空白

现象

后端残留脚手架级单测/e2e；前端缺少系统测试脚本；两端未见 GitHub Actions 等工作流。

  • 没有 CI 时，权限、abort 落库、检索可见性等改动极易静默回退。
  • 现有 e2e 若仍期望 Hello World! 且未对齐全局前缀 /api，说明测试已与产品脱节。

P1 前端 refresh token 存了却未形成闭环

现象

本地存了 refresh token，但 401 时直接清登录踢回登录页，未调用 refresh 接口续期。

原因
  • 后端已实现 refresh，前端拦截器未接上，属于「半做完的鉴权方案」。
  • 用户长时停留在聊天页时 access 过期会突然掉线，体感像系统不稳定。
  • token 放 localStorage 本身也放大 XSS 影响面（成熟方案常配合更严 CSP / httpOnly 策略评估）。
证据 / 落点

P1 可观测性不足

现象

以 Nest Logger 为主；健康检查多为进程级 { ok, ts }，不探测 Postgres / ES / Neo4j / Redis / MQ。

原因
  • 本地排障靠终端日志够用；生产需要结构化日志、关联 requestId、依赖存活探针与告警。
  • 对话一轮跨意图、检索、图谱、LLM、TTS，没有 trace 时「慢」和「失败」难以定位到哪一段。

P1 前后端错误契约不统一

现象

前端请求层假定业务错误形如 code/message；后端大量走 Nest 默认异常 JSON，字段与语义不一致。

原因
  • 缺少全局 ExceptionFilter / 统一响应包装。
  • 前端只能「猜」错误结构，导致 toast 文案空、或把校验详情吞掉，运维与客服难复述问题。

P1 聊天停止 / 落库边缘行为

现象

停止生成会 abort 并落库半截（含「（已中断）」）；TTS 可能提前建会话；落库失败仅 warn；前端有本地中断标记但产品「继续」未闭环。

原因
  • 为支持「继续」选择了取消也落库，但空中断、重复落库、仅 TTS 建空会话等边界未产品化定义。
  • 流式管道跨 SDK / Agent / HTTP close，时序竞争下若缺少幂等与明确状态机，会出现「UI 有半截、库里没有」或相反。

P1 RAG 仅有在线「切题」评估，无离线评测集

现象

Agent 环内用 LLM 对检索结果做切题判断（data-eval），但没有黄金问答集、引用正确率、图谱误召回等回归流水线。

原因
  • 在线 grader 解决的是「这一轮要不要再检索」，不是「系统整体是否变差」。
  • 改写意图提示、混合检索参数、图谱 CONTAINS 策略后，没有基准就无法知道是进步还是过召回。

P2 · 体验与加固

P2 「继续」产品化不足

现象

中断已落库，用户可手打「继续」；缺少一键续写、中断态展示规范、与半截答案的合并策略。

原因
  • 后端已按「取消也落库」落地，前端只做了停止 + 本地标「已中断」，产品链路未走完。
  • 成熟聊天产品通常有明确的 Stop / Regenerate / Continue，避免用户猜提示词。

P2 Mermaid 流程图 vs 知识图谱意图易混

现象

用户要「画流程图」时曾被 kb + 图谱预取抢走注意力，只看到图谱卡；现已加启发式关闭图谱并要求输出 mermaid，但仍可能有边界漏网。

原因
  • 产品里同时存在「Neo4j 知识图谱卡」与「Markdown mermaid 流程图」，用户口语都叫「图画出来」。
  • kb 意图默认 allowGraph 预取，与「画 mermaid」目标冲突；需持续收紧意图与 UI 层级（图谱是过程线索，mermaid 是交付物）。

P2 ErrorBoundary、上传校验、ES refresh 等课练残留

现象

前端缺全局 ErrorBoundary；上传限制偏简单（如体积）未必有严格 MIME 白名单；索引写入使用 refresh: true 等利于课练、不利吞吐的策略。

原因
  • 演示与正确性优先时，会打开 ES refresh、放宽上传校验。
  • 生产需要失败隔离（单组件崩不白屏）、上传防马甲文件、索引异步 refresh 换吞吐。

P2 前端 AuthGuard 只看「有没有 token」

现象

路由守卫用「localStorage 是否有 access token」判断已登录，不解析过期时间。

原因
  • 实现简单，依赖请求 401 再踢出。
  • 过期 token 仍会被当成已登录进入页面，造成闪屏、空数据或一串失败请求。
证据 / 落点

frontend/src/components/AuthGuard.tsx

P2 聊天 SSE 请求头里的 Authorization 易过期

现象

流式聊天 transport 在发起时带上 Bearer；长会话中 access 过期不会像 Axios 拦截器那样自动 refresh 后续 chunk。

原因
  • SSE/fetch 流与普通 JSON 请求生命周期不同，续期策略要单独设计（开流前确保新 token、或短 access + 心跳）。
  • 与 P1「refresh 闭环」叠加：没有统一续期，长回答中途失败会被误判为模型/网络问题。
证据 / 落点
