目标与验收

本课只聚焦「用户注册 → 邮件激活 → 才能登录」这一条链路， 按 origin v8 的实现方式手敲对齐：Redis 存激活 token、MailerModule 发信、 数据库 email_verified / status 双字段门禁。

本课只写讲义：请在练习仓 knowledge-hub-backend 自己改 src/； 对照答案看 knowledge-hub-backend-origin（分支 v8 或 main 的 auth 模块）。
验收清单
  1. REQUIRE_EMAIL_VERIFICATION=false：注册后立即可登录（与 v8 默认行为一致）
  2. REQUIRE_EMAIL_VERIFICATION=true 且注册带 email：返回「请查收邮件」；未激活登录 → 401 账户未激活，请先验证邮箱
  3. 邮件里的 token 调 GET /auth/verify-email?token=… 成功后，同一账号可登录
  4. 激活 token 存 Redis，重启 Nest 后 token 仍有效（24h 内）
  5. 同一用户重复注册不会有多条有效 token（重发时旧 token 作废——本课未实现「重发接口」，但 createToken 已预留双向索引）
  6. SMTP 发信失败时：Redis 里的 token 被清理，接口返回 400 激活邮件发送失败
前置：第 2 课 JWT 登录已通；Postgres 用户表已有 kh_user。 本课需要 Redis + SMTP（或 MailHog 本地收信）。 若你刚学完第 8 课内存版，本课就是把激活链路升级到 origin v8 形态。

概念与状态机

端到端时序

POST /auth/register → AuthService.register() → UserService.register(requireEmailVerification=true) → kh_user: email_verified=0, status=0 → EmailActivationService.createToken(userId) // Redis 双向 key，TTL 24h → EmailService.sendActivationEmail() // 链接含 APP_PUBLIC_URL ← { message: "注册成功，请查收邮件激活账户", emailVerificationRequired: true } 用户点击邮件链接 GET /auth/verify-email?token=xxx → EmailActivationService.consumeToken() // 校验 + 删除 Redis key → UserService.activateEmail(userId) // email_verified=1, status=1 ← { message: "账户激活成功，请登录" } POST /auth/login → UserService.validateCredentials() → emailVerified===0 → 401「账户未激活，请先验证邮箱」 → 否则校验密码 → 签发 JWT

    import { Injectable, OnModuleDestroy } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import Redis from 'ioredis';

@Injectable()
export class RedisService implements OnModuleDestroy {
  private readonly client: Redis;

  constructor(private readonly config: ConfigService) {
    const password = this.config.get<string>('REDIS_PASSWORD');
    this.client = new Redis({
      host: this.config.get<string>('REDIS_HOST', 'localhost'),
      port: this.config.get<number>('REDIS_PORT', 6379),
      password: password || undefined,
      db: this.config.get<number>('REDIS_DB', 0),
      maxRetriesPerRequest: 3,
    });
  }

  async get(key: string): Promise<string | null> {
    return this.client.get(key);
  }

  async set(key: string, value: string, ttlSeconds?: number): Promise<void> {
    if (ttlSeconds !== undefined) {
      await this.client.set(key, value, 'EX', ttlSeconds);
      return;
    }
    await this.client.set(key, value);
  }

  async del(key: string): Promise<void> {
    await this.client.del(key);
  }

  async ttl(key: string): Promise<number> {
    return this.client.ttl(key);
  }

  async onModuleDestroy(): Promise<void> {
    await this.client.quit();
  }
}

  4. EmailActivationService（origin v8 完整）

    src/auth/email-activation.service.ts

    import { Injectable } from '@nestjs/common';
import { randomBytes } from 'crypto';
import { RedisService } from '../redis/redis.service';

const TOKEN_PREFIX = 'email:activation:token:';
const USER_PREFIX = 'email:activation:user:';
export const ACTIVATION_TOKEN_TTL_SECONDS = 24 * 3600;

/** 邮箱激活令牌（Redis 存储，24 小时有效） */
@Injectable()
export class EmailActivationService {
  constructor(private readonly redis: RedisService) {}

  private tokenKey(token: string): string {
    return `${TOKEN_PREFIX}${token}`;
  }

  private userKey(userId: string): string {
    return `${USER_PREFIX}${userId}`;
  }

  async createToken(userId: string): Promise<string> {
    const existing = await this.redis.get(this.userKey(userId));
    if (existing) {
      await this.redis.del(this.tokenKey(existing));
    }

    const token = randomBytes(32).toString('hex');
    // token → userId：用户点激活链接时，用 token 查出要激活的账号
    await this.redis.set(
      this.tokenKey(token),
      userId,
      ACTIVATION_TOKEN_TTL_SECONDS,
    );
    // userId → token：同一用户只保留一个有效 token，重发时先按 userId 找到并作废旧的
    await this.redis.set(
      this.userKey(userId),
      token,
      ACTIVATION_TOKEN_TTL_SECONDS,
    );
    return token;
  }

  /** 校验并消费 token，返回 userId */
  async consumeToken(token: string): Promise<string | null> {
    const userId = await this.redis.get(this.tokenKey(token));
    if (!userId) return null;

    await this.redis.del(this.tokenKey(token));
    await this.redis.del(this.userKey(userId));
    return userId;
  }

  async deleteByToken(token: string): Promise<void> {
    const userId = await this.redis.get(this.tokenKey(token));
    await this.redis.del(this.tokenKey(token));
    if (userId) {
      await this.redis.del(this.userKey(userId));
    }
  }
}

    Redis key 示例：

    • email:activation:token:<64位hex> → userId
    • email:activation:user:<userId> → token

  username: string;
  password: string;
  email?: string;
  realName?: string;
  requireEmailVerification?: boolean;
}): Promise<{
  userId: string;
  emailVerificationRequired?: boolean;
}> {

  if (exists) throw new ConflictException('用户名已存在');
  if (input.email) {
    const emailUsed = await this.findByEmail(input.email);
    if (emailUsed) throw new ConflictException('邮箱已被使用');
  }

  const userId = nextSnowflakeId();
  const needVerify = input.requireEmailVerification && !!input.email;
  const user = this.userRepo.create({
    id: userId,
    username: input.username,
    password: await hash(input.password, 10),
    email: input.email ?? null,
    realName: input.realName ?? null,
    status: needVerify ? 0 : 1,
    emailVerified: needVerify ? 0 : 1,
  });
  await this.userRepo.save(user);
  await this.assignRole(userId, RoleCode.USER);

  return {
    userId,
    emailVerificationRequired: needVerify,
  };
}

  7. AuthService：编排注册与验证

    src/auth/auth.service.ts

    private requireEmailVerification(): boolean {
  return (
    this.config.get<string>('REQUIRE_EMAIL_VERIFICATION', 'false') === 'true'
  );
}

async register(
  dto: RegisterDto,
): Promise<{ userId: string; message: string; emailVerificationRequired?: boolean }> {
  const result = await this.userService.register({
    ...dto,
    requireEmailVerification: this.requireEmailVerification(),
  });

  if (result.emailVerificationRequired && dto.email) {
    const token = await this.emailActivation.createToken(result.userId);
    try {
      await this.emailService.sendActivationEmail(
        dto.email,
        dto.username,
        token,
      );
    } catch {
      await this.emailActivation.deleteByToken(token);
      throw new BadRequestException('激活邮件发送失败，请稍后再试');
    }
    return {
      userId: result.userId,
      message: '注册成功，请查收邮件激活账户',
      emailVerificationRequired: true,
    };
  }

  return {
    userId: result.userId,
    message: '注册成功，请登录',
  };
}

async verifyEmail(token: string): Promise<{ message: string }> {
  const userId = await this.emailActivation.consumeToken(token);
  if (!userId) {
    throw new BadRequestException('激活链接无效或已过期');
  }
  const message = await this.userService.activateEmail(userId);
  return { message };
}
    发信失败回滚：若 SMTP 报错，必须 deleteByToken， 否则 DB 里用户已是「未激活」，Redis 却留着永远用不了的 token，用户无法重试（v8 未提供重发 API，需手动删用户或补接口）。

    场景操作预期

设计决策

为什么 token 存 Redis 而不是 JWT？

激活链接需要可撤销、可一次性消费、可设 TTL。 自包含 JWT 难以在服务端「作废旧链接」或保证单次使用； Redis 存 opaque token，consumeToken 读后即删，语义清晰。

为什么 token 与 userId 双向索引？

正向：token → userId 供用户点链接激活。 反向：userId → token 供「同一用户再次 createToken」时删掉旧链，避免多条有效激活 URL 并存。 origin v8 注册路径只会 create 一次；双向索引是为将来「重发激活邮件」预留。

为什么未激活时 status 也设为 0？

v8 把「未激活」与「管理员禁用」都映射到 status=0，登录时优先看 emailVerified 给出更明确的 401 文案。 activateEmail 同时把 status 拉回 1，避免只改 verified 字段导致边缘状态不一致。

为什么 GET 而不是 POST verify-email？

邮件里的链接必须是可点击的 URL；GET + query token 是常见 magic link 形态。注意 token 会出现在访问日志里，生产应走 HTTPS。

常见报错

现象排查
注册成功但没收到邮件REQUIRE_EMAIL_VERIFICATION=true？请求 body 是否带 email？查 SMTP / MailHog；看 Nest 是否 400「激活邮件发送失败」
登录 401「账户未激活」先 verify-email；查 DB email_verified 是否为 0
verify 400 链接无效token 是否过期（24h）；是否已点过一次（consume 后删除）；Redis 是否连对 db
重启后 token 失效是否仍在用课 8 内存 Map；确认 EmailActivationService 已改 Redis 版
邮件链接 404APP_PUBLIC_URL 是否指向 Nest 服务根；前端若单独部署，链接应指 API 域名
Mailer 连接超时MAIL_PORT / MAIL_SECURE；QQ 邮箱需用授权码而非登录密码
注册 409 邮箱已被使用正常；换邮箱或删测试用户

说明：origin v8 没有 重发接口，但 EmailActivationService.createToken 里的 userId → token 反向索引 就是为此预留的。本节是可选加练：你在练习仓自己加代码；origin 对照仓仍保持不变。

要解决什么问题

  • 用户注册后邮件进垃圾箱 / 过期，需要「再发一封」
  • 注册时 SMTP 失败，DB 已有未激活用户但无有效 token（主链路已 deleteByToken，必须能重发）
  • 重发时必须作废旧链接，同一时刻只保留一条有效激活 URL

接口设计（建议）

项选择原因
路由POST /auth/resend-activation-email与 register 对称；公开接口加 @Public()
入参{ "email": "..." }用户记得邮箱，不记得用户名
响应固定文案，不暴露邮箱是否存在防枚举（与业界忘记密码一致）
冷却60 秒内不可重复发对齐 origin 重置码 RESET_CODE_COOLDOWN_SECONDS
前置仅 REQUIRE_EMAIL_VERIFICATION=true 时有意义开关关闭时可直接返回成功文案
POST /auth/resend-activation-email { email } → findByEmail(email) → 用户不存在 / 已激活 → 200 统一文案（不泄露） → emailVerified=0 → 检查 Redis userKey TTL（冷却） → createToken(userId) // 内部会删旧 token → sendActivationEmail → 失败则 deleteByToken ← { message: "若该邮箱存在未激活账户，激活邮件已发送" }

Step 2 · EmailActivationService 补 TTL 查询

复用已有 userKey 的 Redis TTL 做冷却，不必新增 key：

/** 返回 userId 对应激活 token 的剩余秒数；-2 表示 key 不存在 */
async getUserTokenTtl(userId: string): Promise<number> {
  return this.redis.ttl(this.userKey(userId));
}

在文件顶部常量区追加（与 origin 重置码冷却同思路）：

export const ACTIVATION_RESEND_COOLDOWN_SECONDS = 60;

Step 3 · AuthService.resendActivationEmail

src/auth/auth.service.ts

import {
  EmailActivationService,
  ACTIVATION_TOKEN_TTL_SECONDS,
  ACTIVATION_RESEND_COOLDOWN_SECONDS,
} from './email-activation.service';
import { ResendActivationEmailDto } from './dto/auth.dto';

private readonly resendActivationMessage =
  '若该邮箱存在未激活账户，激活邮件已发送';

async resendActivationEmail(
  dto: ResendActivationEmailDto,
): Promise<{ message: string }> {
  if (!this.requireEmailVerification()) {
    return { message: this.resendActivationMessage };
  }

  const user = await this.userService.findByEmail(dto.email);
  if (!user || user.emailVerified === 1) {
    return { message: this.resendActivationMessage };
  }

  // 与 password reset 相同算法：TTL 仍接近满值说明刚发过
  const ttl = await this.emailActivation.getUserTokenTtl(user.id);
  if (ttl > ACTIVATION_TOKEN_TTL_SECONDS - ACTIVATION_RESEND_COOLDOWN_SECONDS) {
    throw new BadRequestException('激活邮件已发送，请稍后再试');
  }

  const token = await this.emailActivation.createToken(user.id);
  try {
    await this.emailService.sendActivationEmail(
      dto.email,
      user.username,
      token,
    );
  } catch {
    await this.emailActivation.deleteByToken(token);
    throw new BadRequestException('激活邮件发送失败，请稍后再试');
  }

  return { message: this.resendActivationMessage };
}

Step 4 · Controller

@Public()
@Post('resend-activation-email')
resendActivationEmail(@Body() dto: ResendActivationEmailDto) {
  return this.authService.resendActivationEmail(dto);
}

扩展验收 curl

export BASE=http://localhost:3000

# 1) 先注册未激活用户（REQUIRE_EMAIL_VERIFICATION=true）
curl -s -X POST "$BASE/auth/register" \
  -H 'Content-Type: application/json' \
  -d '{"username":"bob_resend","password":"123456","email":"bob@example.com"}' | jq

# 2) 重发（应 200 + 统一文案）
curl -s -X POST "$BASE/auth/resend-activation-email" \
  -H 'Content-Type: application/json' \
  -d '{"email":"bob@example.com"}' | jq

# 3) 60 秒内再发 → 应 400「激活邮件已发送，请稍后再试」
curl -s -X POST "$BASE/auth/resend-activation-email" \
  -H 'Content-Type: application/json' \
  -d '{"email":"bob@example.com"}' | jq

# 4) 不存在的邮箱 → 仍 200 统一文案（防枚举）
curl -s -X POST "$BASE/auth/resend-activation-email" \
  -H 'Content-Type: application/json' \
  -d '{"email":"nobody@example.com"}' | jq

# 5) 旧 token 应失效：用注册时的 token verify → 400；用新邮件 token → 成功
curl -s "$BASE/auth/verify-email?token=$OLD_TOKEN" | jq
curl -s "$BASE/auth/verify-email?token=$NEW_TOKEN" | jq

自测补充项

场景预期
重发后点旧邮件链接400 激活链接无效或已过期（createToken 已删旧 key）
已激活用户重发200 统一文案，不发信
注册 SMTP 失败后重发能拿到新 token 并完成激活
常见坑： ① 冷却判断写反（应比较 ttl > TTL - COOLDOWN）； ② 已激活用户也发信（浪费且泄露状态）； ③ 返回「该邮箱未注册」类文案（被用来扫库）。
