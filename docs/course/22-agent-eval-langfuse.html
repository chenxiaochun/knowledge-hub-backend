1. 为什么要测 Agent？

课 20/21 的对话链路是： 意图路由 → 可选图谱预取 / RAG / 联网 → Agent 流式作答。 改一句 prompt、换一个模型，肉眼看几条对话很难判断「整体有没有回退」。

本课把能力拆成两层（别混成一件事）：

能力回答的问题你怎么用
分层金标评测 这类题对了百分之几？改 prompt 后有没有掉点？ 本地 pnpm eval:intent + JSONL 金标
Langfuse 观测 这一轮调了哪些模型/工具、耗时、失败卡在哪？ Cloud UI 里按 session 看 trace
接了 Langfuse ≠ 有了准确率。 Langfuse 告诉你「发生了什么」；金标评测告诉你「对不对、退没退」。 第一期（P0）准确率只盯 L1：意图 + allowGraph / allowWeb。
离线回归 eval/datasets/*.jsonl → eval/runners/run-intent.ts → reports/*.json 在线对话 ai-stream + createLangfuseHandler → Langfuse Cloud（看链路）

2. 准确率、混淆矩阵、金标（白话）

金标是什么？

金标 = 你事先写好的「标准答案小表」。每行一道题：问句 + 期望意图 + 期望工具开关。 跑分脚本用同一套线上路由逻辑预测，再和期望比对。

准确率

  • Intent Accuracy：预测意图 === 期望意图 的比例
  • allowGraph / allowWeb Accuracy：两个开关各自与期望一致的比例

混淆矩阵

一张「真实 intent × 预测 intent」的计数表。 对角线是答对；非对角线是「把 kb 判成 web」这类易混错误——比一个总百分比更有用。

仓库已有样例集 eval/datasets/golden-v1.jsonl （约 15 题，五类 intent 都有）。报告样例见 eval/reports/sample-report.json。

3. Langfuse 是什么；和金标差在哪

金标评测Langfuse
何时跑离线批量（改 prompt 后回归）线上每轮对话（可开关）
输出准确率、混淆矩阵、失败列表trace / span / token / 耗时
依赖金标文件 + LLM 密钥Cloud 项目 + API key
默认手动执行脚本LANGFUSE_ENABLED!=true 时完全不发

流式主路径在意图识别完成后调用 createLangfuseHandler，挂到 Agent stream 的 callbacks； 未启用时返回 undefined，行为与现网一致。

P0 观测范围：仅流式路径。 Langfuse 只挂在 ai-stream / UI Message 流式对话上； 同步 POST /ai/chat 尚未埋点，开了开关也不会在 Cloud 里看到同步请求的 trace。

4. 注册 Cloud → 配 env → 找 trace

  1. 注册 Langfuse Cloud
    打开 cloud.langfuse.com （按账号区域也可能是欧盟等站点），新建项目，复制 Public Key 与 Secret Key。
  2. 写入本地 .env（勿提交仓库、勿把真实 key 贴进文档）： 
    LANGFUSE_ENABLED=true
LANGFUSE_PUBLIC_KEY=pk-lf-xxxxxxxx
LANGFUSE_SECRET_KEY=sk-lf-xxxxxxxx
# 可选；不设则默认 https://cloud.langfuse.com
# LANGFUSE_BASE_URL=https://cloud.langfuse.com
    启动日志会提示是否启用及 baseURL（不打印 secret）。 缺 key 或未设 true 时应用与现网一致。
  3. 重启后端，用前端或 API 打一轮流式对话（POST /ai/chat/stream / UI Message stream；同步 POST /ai/chat 当前不会出 trace），记下返回的 sessionId （会话 id；Langfuse 里用同一字段关联）。
  4. 在 UI 里找 trace
    • 打开 Langfuse → Traces（或 Sessions）
    • 用 sessionId 过滤，或按时间找最近一条
    • 应能看到 tags 类似 stream、ai-chat、intent:kb，以及脱敏后的 intent / 开关元数据
内部意图改写仍用空 LangChain callbacks，避免 structured JSON 漏进 SSE。 观测靠外层 handler + OTel；若开了 Langfuse，请确认流式响应里没有改写用的原始 JSON。

5. 按五类 intent 标 10～15 题

意图枚举与代码一致：

intent直觉常见开关
chitchat寒暄、致谢图关、网关
profile问本人信息 / 改回答偏好图关、网关
kb内部制度、流程、文档常开图、关网
web公开时效（天气、汇率）关图、开网
kb_then_web内部标准 + 外部时效图网都可开

一行一条 JSON，追加到 eval/datasets/golden-v1.jsonl：

{
  "id": "kb-practice-001",
  "question": "差旅报销需要谁审批？",
  "expect": {
    "intent": "kb",
    "allowGraph": true,
    "allowWeb": false
  },
  "notes": "制度类；图谱可选开启"
}

造题原则

  • 五类尽量均衡；故意加易混题（闲聊 vs 制度、要不要联网）。
  • 只标有把握的；不确定可设 "skip": true 或写在 notes。
  • 仓库已有约 15 题样例；练习时再扩 10 题即可，目标可到 30～50。
练习任务：打开现有 jsonl，对照格式自己加 ≥10 行（或改 notes 复盘易混点）， 再跑下一节的 pnpm eval:intent。

6. 跑 pnpm eval:intent，读报告

在仓库根目录（需已配置 LLM 相关 env，与线上一致即可）：

pnpm eval:intent

终端会打印每题 expect / pred / OK|FAIL，以及汇总：

[eval:intent] mode=standalone
chitchat-001	expect=chitchat	pred=chitchat	OK
...
intentAccuracy=100.0% allowGraph=100.0% allowWeb=100.0%
report: eval/reports/2026-10-23T....json
字段含义
modenest：成功拉起 Nest ApplicationContext；若因 TTS 等中间件失败，会降级 standalone（直接 ChatOpenAI + ChatQueryRewriteService），结果仍可用
summary.intentAccuracy意图准确率（0～1）
summary.confusion混淆矩阵
summary.failures答错题列表（id + expect/pred）
rows逐题明细
eval/reports/ 默认 gitignore；可参考已提交的 sample-report.json 了解结构。每次跑分会新写一份带时间戳的 JSON。

7. 故意改坏再跑（建立回归直觉）

目的不是破坏生产，而是亲手感受「准确率会掉」：

  1. 先跑一遍 pnpm eval:intent，记下 intentAccuracy（基线）。
  2. 在本地副本里临时改乱路由提示（例如 ChatQueryRewriteService 里的 ROUTE_PROMPT：把「制度类」写成「一律走 web」）， 不要提交、不要推生产。
  3. 再跑 pnpm eval:intent，对比准确率与 failures / 混淆矩阵。
  4. 用 git checkout --（或 IDE 还原）恢复文件，再跑第三遍确认回到基线。
只描述练习步骤；真实改 prompt 前请有金标基线。本课不要求你真的改坏生产配置。

8. 如何加题；P1 / P2 预告

加题

  • 继续往 golden-v1.jsonl 追加行，或新建 golden-v2.jsonl（需改 runner 读路径）。
  • 保持类别均衡；每加一批就跑分，避免「只测自己拿手的题」。

附录 · 自托管 BASE_URL

默认走 Cloud：https://cloud.langfuse.com。 若团队自建 Langfuse，只需改环境变量（仍不要把真实 key 写进仓库）： 

LANGFUSE_ENABLED=true
LANGFUSE_PUBLIC_KEY=pk-lf-xxxxxxxx
LANGFUSE_SECRET_KEY=sk-lf-xxxxxxxx
LANGFUSE_BASE_URL=https://langfuse.example.com

P0 不强制自托管；配错区域 / BASE_URL 时 Cloud 里会看不到数据，先核对启动日志里的 baseURL。
